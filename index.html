Avant-projet de vidéoprotection IP pour un marché public Alternance

Septembre 2026, Ensio Sud, Bassens, BUT GEII 3e année

  • Concevoir
  • Intégrer

Un établissement culturel public remplace sa vidéosurveillance analogique par un système IP. Pour la fiche technique du cahier des clauses techniques (CCTP) de l'appel d'offres, j'ai conçu l'architecture réseau : synoptique, plan d'adressage, répartition des caméras par zone et dimensionnement des switchs et des enregistreurs.

61 camérasréparties sur dix switchs PoE de zone
96 voiesd'enregistrement, réserve comprise
30 %de ports laissés libres pour les évolutions
Choix techniques

Choix techniques

  • Un VLAN dédié à la vidéoprotection, en adressage statique : aucune caméra ne dépend d'un serveur DHCP.
  • Les switchs existants sont conservés, six switchs PoE neufs complètent les zones saturées ou non couvertes.
  • Aucune liaison cuivre de plus de 100 m sans switch intermédiaire.
  • Enregistrement sur 30 jours avec écrasement automatique, tête de réseau secourue par onduleur.
  • Un poste de sécurité dédié à la supervision et au report d'images.

Livrables

Synoptique réseau, plan d'adressage, matrice de flux et notes techniques, réalisés sous draw.io. Les documents complets restent internes à l'entreprise.

Détection d'objets par IA embarquée sur caméras IP

Avril à juillet 2026, stage de 2e année, Ensio, pôle vidéosurveillance de Bassens

  • Concevoir
  • Vérifier
  • Maintenir
  • Intégrer
  • Manager

Une caméra « intelligente » reconnaît des personnes ou des véhicules, mais peut-elle apprendre un objet quelconque ? J'ai comparé l'apprentissage d'objets personnalisés sur les caméras de plusieurs marques, puis fait remonter ces détections sous forme d'alarmes dans le logiciel de supervision Genetec Security Center. Deux chaînes complètes ont été validées, i-PRO et Hanwha, et documentées en tutoriels pour le pôle.

3 imagespar classe pour distinguer deux canettes sur Hanwha, contre 30 à 45 pour un extincteur sur i-PRO
2 chaînesvalidées de la caméra jusqu'à l'alarme dans Genetec
3 tutorielslivrés au pôle : i-PRO, Hanwha et alarme intrusion Ajax
Démarche, choix et imprévus

Démarche

  • Cartographie des marques : apprentissage personnalisé sans code chez i-PRO et Hanwha, développement ACAP obligatoire chez Axis, aucun chez Pelco.
  • Réglage de l'image avant l'apprentissage : gain bas, WDR désactivé, obturateur rapide.
  • Pour chaque marque : capture, étiquetage, entraînement, déploiement dans la caméra, puis règle d'alarme.
  • Dans Genetec : observation de l'événement réel, puis création de l'alarme et de l'automatisation.
  • Vérification de chaque déclenchement dans le journal d'événements de la caméra, horloge synchronisée par NTP.

Choix argumentés

  • Détection côté serveur avec YOLO testée puis écartée : plus de latence, et des événements plus fragiles à injecter dans le logiciel de supervision.
  • Genetec retenu face à WAVE, dont la version gratuite n'affiche pas les classes personnalisées.

Imprévus diagnostiqués

  • Logiciel WiseDetector bloqué au lancement : cause trouvée dans les journaux, un runtime .NET 5.0 en 32 bits manquant.
  • Caméra Pelco de prêt muette : alimentation PoE, balayage réseau, table ARP, adresse par défaut et réinitialisation contrôlés, puis port RJ45 endommagé signalé au fournisseur avec photos.

Poste automatisé de chargement et déchargement En cours

2026, SAE de 3e année en équipe, plateforme Festo CP Lab

  • Concevoir

Une station qui range des coques dans un magasin ou les en ressort, selon ce qui arrive sur la palette. Le convoyeur amène la palette sous un bras robot cartésien, qui fait le transfert. Deux automates se partagent le poste : un ET 200SP (CPU 1512SP) pour la station et le convoyeur, un S7-1200 (CPU 1214C) pour le robot, qui échangent leurs données en iDevice sur PROFINET.

Dans l'équipe, je conçois les Grafcets du poste, en niveaux 1 et 2, puis je les traduis en Ladder.

  1. SécuritéArrêt d'urgence, force la conduite
  2. ConduiteModes automatique, semi-manuel et manuel
  3. Production stationConvoyeur et palette
  4. Production robotTransferts magasin et palette

FaitGrafcets de conduite, de production de la station et du robot, et de prise d'origine du robot, en niveaux 1 et 2. Table des variables des deux automates.

En coursProgrammation en Ladder, puis essais sur la station.

Cahier des charges et choix de conception

Cahier des charges

  • Palette vide : le robot y dépose une coque prise dans le magasin. Coque assemblée : elle est rangée en stock.
  • Un seul appui sur Start lance la production automatique.
  • Défaut signalé si le magasin est vide pour un déchargement, ou plein pour un chargement.
  • Prise d'origine du robot après une mise sous tension ou un Reset.

Choix de conception

  • Grafcets hiérarchisés : la sécurité force la conduite, qui maintient la production à son étape initiale tant que le poste n'est pas prêt.
  • Station et robot synchronisés par une demande et un signal de fin de séquence, échangés entre les deux automates.
  • Pince et vérin commandés en actions mémorisées, pour que la pince ne lâche pas la coque au changement d'étape.
  • En Ladder, chaque transition active l'étape suivante et désactive la précédente, dans un seul réseau.

Matériel et outils

ET 200SP CPU 1512SP, S7-1200 CPU 1214C, iDevice PROFINET, axes X et Z motorisés, vérin et pince pneumatiques, convoyeur Festo, TIA Portal, Ladder.

Mugochaud, enceinte chauffante régulée

2026, BUT GEII 2e année, en binôme

  • Concevoir
  • Vérifier
  • Intégrer
  • Manager

Une enceinte qui chauffe et maintient un mug à 50 °C, pilotée par un automate Siemens S7-1200. J'ai câblé la partie puissance de l'armoire, programmé en SCL les Grafcets de sécurité et de production, et calculé sous Matlab le correcteur PI de la régulation.

6 min 20 spour atteindre 50 °C, objectif sous 10 min
±0,1 °Cécart de la régulation PI une fois stabilisée
5,016 savant déverrouillage de la porte, objectif 5 s
Cahier des charges, matériel et code

Cahier des charges

  • Atteindre et réguler 50 °C en moins de 10 minutes.
  • Couper la chauffe instantanément si la porte s'ouvre.
  • Verrouiller la porte par électro-aimant en moins d'une seconde.
  • Déverrouiller 5 secondes exactement après la demande d'arrêt.

Ce que j'ai fait

  • Dimensionnement et câblage de la puissance (section AWG 16).
  • Programmation SCL de l'automate à partir des Grafcets.
  • Calcul du correcteur PI sous Matlab et intégration dans l'automate.
  • Campagne d'essais avec l'outil de trace de TIA Portal.

Matériel et outils

Siemens S7-1200 (CPU 1215C), TIA Portal V18, SCL, Matlab, sonde PT1000, capteur SN04N, électro-aimant 24 V, résistance HS50.

Extrait : régulation PI en SCL

IF "dbPID".xMode_Activate = TRUE THEN

    // Calcul de l'erreur (Consigne - Mesure)
    "dbPID".rEk := "dbPID".rConsigne - "dbFormation".rTemperatureActuelle;

    // Calcul de la commande Uk
    "dbPID".rUk := "dbPID".rUkm1 + (("dbPID".rTe / "dbPID".rTi) + 1.0)
                  * "dbPID".rC0i * "dbPID".rEk
                  - ("dbPID".rC0i * "dbPID".rEkm1);

    // Limitation de la commande (0 à 27648)
    IF "dbPID".rUk > 27648.0 THEN
        "dbPID".rUk := 27648.0;
    ELSIF "dbPID".rUk < 0.0 THEN
        "dbPID".rUk := 0.0;
    END_IF;

    // Envoi vers la sortie analogique
    "xAQ0" := REAL_TO_INT("dbPID".rUk);

    // Mémorisation des variables pour la prochaine interruption
    "dbPID".rUkm1 := "dbPID".rUk;
    "dbPID".rEkm1 := "dbPID".rEk;

ELSE
    // Si GPN ou GS a coupé la régulation, on s'assure que tout reste à 0
    "dbPID".rUk   := 0.0;
    "dbPID".rUkm1 := 0.0;
    "dbPID".rEk   := 0.0;
    "dbPID".rEkm1 := 0.0;
    "xAQ0"         := 0;
END_IF;

Robot guidé par une caméra Wi-Fi

2025 à 2026, BUT GEII 2e année, projet tutoré

  • Concevoir

La caméra n'est pas sur le robot : elle filme l'arène, repère le robot et sa cible, et envoie leurs positions en UDP sur le réseau Wi-Fi. J'ai écrit en C++ pour l'ESP32 deux bibliothèques, l'une pour le déplacement, l'autre pour calculer l'angle à corriger à partir de ces données.

Code de pilotage

Extrait : lecture des trames et pilotage

// Lecture trame UDP caméra → calcul vectoriel → pilotage moteurs
// Wi-Fi: sumoProject · UDP port 5000 · ESP32 · ID robot = 10

#include <WiFi.h>
#include "vectorLab.h"
#include "motorLab.h"

#define k 30
const short int MyRobot = 10;
int VectorRobot[3], VectorTarget[3];
int statecontrol = 0;

void lire_tram_reseau() {
    char packetBuffer[255];
    unsigned short int* intBuffer;
    int packetSize = udp.parsePacket();

    if (packetSize) {
        int len = udp.read(packetBuffer, 255);
        intBuffer = (unsigned short int*)packetBuffer;

        if (len > 0 && len <= 28) {
            // Calcul des vecteurs Robot et Cible selon mon ID
            if (intBuffer[7] == MyRobot) {
                VectorRobot[0]  = intBuffer[8]  - intBuffer[12];
                VectorRobot[1]  = intBuffer[9]  - intBuffer[13];
                VectorTarget[0] = intBuffer[3]  - intBuffer[10];
                VectorTarget[1] = intBuffer[4]  - intBuffer[11];
            } else {
                VectorRobot[0]  = intBuffer[1]  - intBuffer[5];
                VectorRobot[1]  = intBuffer[2]  - intBuffer[6];
                VectorTarget[0] = intBuffer[10] - intBuffer[3];
                VectorTarget[1] = intBuffer[11] - intBuffer[4];
            }

            double angleRadian = angle_radian(VectorRobot, VectorTarget);

            // État 0 : alignement sur la cible par rotation
            if (statecontrol == 0) {
                if (angleRadian > 0)  droite(angleRadian * k);
                else                  gauche(-angleRadian * k);

                if (abs(angleRadian) < 0.2) statecontrol = 1;
            }

            // État 1 : avance avec correction de cap
            if (statecontrol != 0) {
                // Conversion après le produit : (int)angleRadian vaudrait 0 sous 1 rad
                avance(30, (int)(k * angleRadian));
            }
        }
    }
}

void loop() { lire_tram_reseau(); }
